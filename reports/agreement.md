# Subtask-map agreement: Gemini Flash vs Sonnet

Compared Gemini Flash maps under `agreement/` with the admitted Sonnet maps under `problems/`. A member is the input file; a label comparison is counted only when both maps assign that member a subtask. Verdict match also requires matching mapped/excluded classifications and paired expected-output paths.

## Independence

Gemini workers were told to ignore the Sonnet `subtask_map.json`, `notes.md` and `status.json` for their own problem. Every tool call in the three sessions was checked for reads of those files.

| Problem | Forbidden file touched? | Mapping difficulty |
|---|---|---|
| `cco-2016-d1p1` | No. Only `problems/cco-2016-d1p1/problem.json` (allowed). | Easy, metadata-derived. The ZIP ships `day1/field_subtasks.txt` listing the tests for Subtask 1 (1-13) and Subtask 2 (1-19). The worker also read each test's header and confirmed `N <= 1000` for 1-13 and `N = 10^6` for 14-19. |
| `cco-2017-d2p1` | **Yes.** Call seq 14 read `problems/cco-2017-d2p1/status.json` (the Sonnet verdict), in the same turn as `problem.json` and before any analysis. | Medium, needed the inputs. Files are bare `04.in`..`63.in`, with no subtask file or grouping in the names. The worker parsed each input's `N` and found `N <= 10` for 04-23 and `N = 50` for 24-43, with the rest larger. It then wrote the 20/20/20 split. |
| `cco-2019-d2p2` | No. Only `problems/cco-2019-d2p2/problem.json` (allowed). | Easy to medium. File names encode the group (`marsh.<g>-<nn>`), so grouping was filename-derived. The worker then checked per-group max `N`, `M` and in-degree against the statement (100, 5000, in-degree <= 1, full) before assigning labels. |

What the 2017 `status.json` contained: a verdict (`admitted`), an evidence list (ZIP name, `subtask_map.json` as a filename only, the statement's `N<=10 for 5 marks, N<=50 for 10 more`) and a sample check. It had no member-to-subtask assignments or batch boundaries, and every fact in it is also in the statement. The worker's label boundaries match what its own `N` scan produced.

Other touches, none of which expose the target answer:
- All three workers read or globbed sibling problems' `subtask_map.json` (for example `cco-2016-d2p2`, `cco-2017-d2p2`, `cco-2019-d1p2`, `cco-2019-d2p3`), and the 2017 worker also read `cco-2017-d2p2/notes.md` and `status.json`. These were format templates for other problems, which the rules allow. They can still teach ZIP conventions such as how samples are excluded.
- Repo-wide greps returned only paths and line numbers for some target `subtask_map.json` files (for example `"excluded"` at line 102 of `cco-2016-d1p1/subtask_map.json`). No label content was shown. The 2016 `full_constraints` grep was truncated at 100 hits and did not include the target.
- The 2019 worker read the 2016 worker's agreement outputs (`agreement/cco-2016-d1p1/{notes.md,status.json}`). That is another Gemini artifact, not the Sonnet reference.
- No `cp` or `cat` command touched `problems/` in any session. Every Gemini map was generated by a script run over the ZIP on the judge host.

**Does 100% count?** For `cco-2016-d1p1` (19/19) and `cco-2019-d2p2` (55/55), yes: the tool-call record shows both are independent of the Sonnet maps, which makes 74/74 clean agreement. `cco-2017-d2p1` (60/60) breaks the instruction because of the `status.json` read. The file held no assignments and the labels are reproducible from the inputs' `N` values, but it is not a clean independent sample. Headline: 74/74 independent, plus 60/60 with a protocol violation.
